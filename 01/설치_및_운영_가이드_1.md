# 냉장고 파먹기 레벨업 챌린지
## 설치 및 운영 가이드 — Apps Script + Make + Discord Webhook 1채널

> **가장 중요한 원칙**
>
> 1. Make와 Apps Script 독립 실행 모드를 동시에 켜지 않습니다.
> 2. Make는 `Run once` 전체 테스트가 끝난 뒤에만 Scheduling을 켭니다.
> 3. Discord Webhook URL은 비밀값입니다. Apps Script에서는 Script Properties의 `DISCORD_WEBHOOK_URL`에만 저장하고, Make Blueprint에는 `__DISCORD_WEBHOOK_URL__`만 유지합니다.
> 4. Discord 공개 메시지에서 참가자를 식별하는 값은 `챌린지닉네임`과 `참가자ID`뿐입니다. 레벨·칭호·진행도는 게임 상태 정보입니다.
> 5. Make 모드의 SCN-02는 Lv.5 완료와 인증서 발급 대기 상태만 기록합니다. PDF 생성·Discord 첨부·Drive fallback은 Apps Script `issuePendingCertificates()`가 담당합니다.

## 1. 패키지 구성과 실제 역할

```text
fridge_challenge_discord_package/
├─ apps_script/
│  ├─ Code.gs
│  └─ appsscript.json
├─ make_blueprints/
│  ├─ 01_signup_welcome.blueprint.json
│  ├─ 02_mission_levelup.blueprint.json
│  ├─ 03_reminder.blueprint.json
│  └─ MAPPING_MANIFEST.json
├─ 설치_및_운영_가이드.md
├─ 빠른시작_체크리스트.md
└─ DISCORD_메시지_예시.md
```

- `Code.gs`: Google 자산 설치, Discord Webhook 안전 설정, Apps Script 독립 실행, 5일 리마인드, 인증서 PDF 생성·Discord 공유를 담당합니다. 버전은 `2.0.0-discord`입니다.
- `appsscript.json`: `Asia/Seoul`, V8 런타임 및 Sheets·Forms·Drive·Slides·외부 HTTP 요청·트리거 관리 권한을 선언합니다.
- `01_signup_welcome.blueprint.json`: 참가 신청 → 중복 확인 → 트래커 생성 → Discord 웰컴 또는 중복 안내.
- `02_mission_levelup.blueprint.json`: 참가자·이메일·사진·순서·중복·필수 설명 검증 → Lv.1~Lv.5 상태 갱신 → Discord 레벨업·오류 안내. **인증서 파일을 즉시 내려받거나 첨부하지 않습니다.**
- `03_reminder.blueprint.json`: 5일 미제출 대상 → Discord 리마인드 → 상태 갱신.
- `MAPPING_MANIFEST.json`: placeholder와 열 재매핑 참고 파일입니다. Make에 Import하지 않습니다.

Blueprint 3종은 계정 연결값이 없는 **조립형 골격**입니다. 가져온 뒤 Google 연결, Spreadsheet, Sheet, 열, 필터, Row number, Form 링크, Discord URL을 Make UI에서 다시 선택해야 합니다.

## 3. Apps Script 설치

### 3.1 프로젝트 만들기

1. `https://script.google.com`에서 새 프로젝트를 만듭니다.
2. 기본 `Code.gs` 내용을 모두 지우고 `apps_script/Code.gs` 전체를 붙여넣습니다.
3. **프로젝트 설정 → 편집기에 `appsscript.json` 표시**를 켭니다.
4. 패키지의 `apps_script/appsscript.json` 전체를 붙여넣고 저장합니다.

### 3.2 OAuth 승인과 자산 생성

1. 함수 선택에서 `setupFridgeChallenge`를 선택하고 실행합니다.
2. 권한 검토에서 운영 DB를 소유할 Google 계정을 선택합니다.
3. 요청 범위는 다음과 같습니다.
   - Google Sheets
   - Google Forms
   - Google Drive
   - Google Slides
   - 외부 HTTP 요청(`script.external_request`)
   - 트리거 관리(`script.scriptapp`)
4. 직접 검토한 프로젝트일 때만 미확인 앱 고급 승인 절차를 진행합니다.
5. 실행 완료 후 로그의 `spreadsheetUrl`, `joinFormUrl`, `missionFormUrl`, `certificateFolderUrl`을 확인합니다.
6. `selfCheckFridgeChallenge()`를 실행하여 `ok=true`인지 확인합니다.

조직 Google Workspace에서 권한 승인이 차단되면 관리자에게 Forms·Drive·Slides·외부 요청·트리거 범위 허용을 요청합니다.

## 4. Discord Incoming Webhook 생성과 비밀 등록

### 4.1 Webhook 만들기

1. 메시지를 게시할 Discord 서버와 채널을 선택합니다.
2. **채널 설정 → 연동(Integrations) → Webhooks**로 이동합니다.
3. 새 Webhook을 만들고 대상 채널을 확인합니다.
4. Webhook URL을 복사하되 문서, 채팅, 시트, 소스 코드, 공개 저장소에 붙여넣지 않습니다.

### 4.2 Apps Script에 안전하게 저장

**스프레드시트에 바인딩된 UI가 있는 경우**

1. 운영 DB를 새로고침합니다.
2. 메뉴 **🍲 냉파 레벨업 → Discord Webhook 안전 입력**을 선택합니다.
3. URL을 입력합니다. 내부적으로 `setDiscordWebhookUrl()`이 Script Properties의 `DISCORD_WEBHOOK_URL`에만 저장합니다.
4. **Discord Webhook 연결 테스트** 또는 `testDiscordWebhook()`을 실행합니다.

**독립형 Apps Script 프로젝트인 경우**

1. Apps Script **프로젝트 설정 → 스크립트 속성**을 엽니다.
2. 속성 이름 `DISCORD_WEBHOOK_URL`을 만들고 URL을 값으로 저장합니다.
3. `setDiscordWebhookUrl()`을 실행해 형식 검증과 CONFIG 상태 갱신을 수행합니다.
4. `testDiscordWebhook()`을 실행합니다.

`CONFIG`에는 URL이 아니라 `DISCORD_WEBHOOK_CONFIGURED=Y/N`만 기록됩니다. 삭제할 때는 `clearDiscordWebhookUrl()`을 사용합니다.

### 4.3 유출 시 회전

1. Discord에서 기존 Webhook을 삭제합니다.
2. 새 Webhook을 만듭니다.
3. Apps Script의 `DISCORD_WEBHOOK_URL`과 Make의 안전한 저장값을 새 URL로 갱신합니다.
4. `testDiscordWebhook()`과 Make의 안전한 테스트를 다시 수행합니다.
5. Blueprint·로그·화면 캡처·저장소에 이전 URL이 남았는지 검사합니다.

## 6. `인증 사진`을 파일 업로드로 교체

Apps Script 설치기는 Google Forms 서비스 제약 때문에 필수 URL 단답형 `인증 사진`을 만듭니다. 파일을 직접 받으려면 운영자가 수동 교체합니다.

1. `CONFIG!MISSION_FORM_EDIT_URL`을 엽니다.
2. 기존 URL 단답형 `인증 사진`을 삭제합니다.
3. **질문 추가 → 파일 업로드**를 선택합니다.
4. 제목을 정확히 `인증 사진`으로 입력합니다.
5. 이미지 파일, 1개 이상, 필수 응답으로 설정합니다.
6. URL 문항과 파일 업로드 문항을 동시에 남기지 않습니다.
7. `setupFridgeChallenge()`를 재실행하여 문항 ID를 갱신합니다.
8. `미션인증_응답`에서 `인증 사진` 헤더가 한 번만 존재하는지 확인합니다.
9. Make SCN-02의 Watch Rows와 사진 필터에서 해당 열을 다시 선택합니다.

파일 업로드 문항은 사전 작성 링크에서 채우지 않습니다. Apps Script 독립 실행기는 다음을 사진 증거로 인정합니다.

- `http://` 또는 `https://` URL
- Google Drive/Docs 링크
- 20자 이상의 Drive 파일 ID 형태

`setupFridgeChallenge()`는 재실행 시 현재 `PROJECT_MODE`와 `STANDALONE_ENABLED` 상태를 보존하도록 수정되어 있습니다. 단, `미션설정`과 `메시지템플릿`은 기본값으로 다시 기록될 수 있으므로 사용자 수정본을 먼저 백업합니다.

## 7. Make Blueprint 가져오기

### 7.1 Import 순서

각 파일을 별도 시나리오로 Import합니다.

1. `01_signup_welcome.blueprint.json`
2. `02_mission_levelup.blueprint.json`
3. `03_reminder.blueprint.json`

`MAPPING_MANIFEST.json`은 참고 파일이며 Import 대상이 아닙니다. 가져온 직후 세 시나리오의 Scheduling은 모두 OFF로 유지합니다.

### 7.2 Google OAuth와 공통 재매핑

모든 Google Sheets 모듈에서:

1. `Connection`에 실제 운영 DB 계정을 연결하고 OAuth를 승인합니다.
2. `Spreadsheet`를 `냉장고 파먹기_운영DB`로 다시 선택합니다.
3. 각 `Sheet`를 목적에 맞게 다시 선택합니다.
4. 동적 열 목록을 새로 불러옵니다.
5. 필터, Update Row 값, Row number를 한국어 헤더 기준으로 다시 선택합니다.

### 7.3 placeholder 교체

- Google 연결 `__IMTCONN__=0` → 실제 Google Sheets 연결
- `/__SPREADSHEET_ID_FROM_CONFIG__` → 운영 DB
- `__SHEET_ID_JOIN_RESPONSE__` → `참가신청_응답`
- `__SHEET_ID_MISSION_RESPONSE__` → `미션인증_응답`
- `__SHEET_ID_TRACKER__` → `레벨업트래커`
- `__ROW_NUMBER__` → Make 모듈이 반환한 실제 Row number 동적 토큰
- `__MISSION_FORM_PREFILL_BASE_URL__` → 실제 미션 Form 또는 사전 작성 링크
- `__DISCORD_WEBHOOK_URL__` → 안전하게 저장한 Webhook URL 매핑

사전 작성 링크는 Form의 **더보기 → 사전 작성 링크 가져오기**로 생성합니다. `참가자ID`와 `제출 레벨`은 동적으로 바꾸되, 공개 Discord 링크에는 이메일을 넣지 않는 것이 현재 Apps Script 정책과 일치합니다. 파일 업로드 문항도 사전 작성하지 않습니다.

### 7.4 Make의 Webhook 비밀 관리

가능하면 Make Team/Organization의 Custom Variable 또는 비밀 관리가 가능한 연결·변수 기능을 사용합니다. UI에서 HTTP 모듈 URL에 직접 넣어야 한다면:

- 화면 공유와 History 캡처에서 URL을 가립니다.
- Blueprint를 재내보내면 실제 URL이 JSON에 포함될 수 있음을 전제로 합니다.
- 외부 공유 전 `__DISCORD_WEBHOOK_URL__`로 되돌리고 실제 `/webhooks/{id}/{token}` URL이 없는지 검사합니다.

### 7.5 시나리오별 확인

**SCN-01 `SCN-01_참가신청_Discord웰컴`**

- Watch Rows: `참가신청_응답`
- Search Rows: `레벨업트래커`, 이메일 중복 검색
- Search Rows 0건이어도 계속 실행하도록 설정
- Add/Update Row의 39열과 Row number 재선택
- Discord 웰컴·중복 HTTP 모듈의 URL과 payload 확인

**SCN-02 `SCN-02_미션인증_검증_Discord레벨업_인증서`**

- Watch Rows: `미션인증_응답`
- Search Rows: `레벨업트래커`, 참가자ID 검색
- 0건이어도 계속 실행하도록 설정
- 참가자 미확인, 이메일 불일치, 사진 누락, 순서 오류, 중복, Lv.1~Lv.5 통과, 필수 설명 누락 필터 재선택
- Lv.1~Lv.4는 다음 레벨을 열고 Discord 상태창을 게시
- Lv.5는 `Lv5상태=완료`, `전체완료여부=완료`, `인증서발급상태=미발급`을 기록
- **인증서 다운로드·multipart 첨부 모듈은 제거되었습니다. `issuePendingCertificates()`가 후속 처리합니다.**

**SCN-03 `SCN-03_5일미제출_Discord리마인드`**

- Search Rows: `레벨업트래커`
- 완료자가 아니며 리마인드 예정일이 지났고 현재 레벨 상태가 `진행중`, 발송 여부가 `N`인 행만 통과
- 성공 시 `AC=Y`, `AD=발송시각`, `AK=성공` 재매핑
- 예약은 매일 `09:00 Asia/Seoul`, 테스트 전 OFF

### 7.6 실행 설정

세 Blueprint 모두 다음을 유지합니다.

- `scheduling.enabled=false`로 Import
- `metadata.scenario.sequential=true`
- `metadata.scenario.slots=1`

Make UI에서도 순차 실행을 켜고 동시 실행 수를 1로 확인합니다.

## 8. 운영 모드 선택 — 반드시 하나만

### 8.1 Make 모드

- `PROJECT_MODE=MAKE_ASSET_ONLY`
- `STANDALONE_ENABLED=N`
- `installStandaloneTriggers()` 실행 금지
- SCN-01~03 사용
- 인증서 전담용 `issuePendingCertificates` 시간 트리거만 별도로 설치

인증서 트리거 설치:

1. Apps Script **트리거 → 트리거 추가**
2. 함수 `issuePendingCertificates`
3. 이벤트 소스 **시간 기반**
4. 시간 타이머 또는 운영량에 맞는 주기 선택
5. 저장하고 권한 승인
6. 운영 전 `issuePendingCertificates()`를 수동 실행해 검증

이 트리거는 Form 제출을 처리하지 않으므로 Make와 함께 사용할 수 있습니다.

### 8.2 Apps Script 독립 실행 모드

1. Make SCN-01~03 Scheduling을 모두 OFF로 끕니다.
2. `CONFIG!MAKE_SCENARIOS_CONFIRMED_OFF=Y`로 설정합니다. 이 확인값이 없으면 `installStandaloneTriggers()`가 중단됩니다.
3. `installStandaloneTriggers()`를 실행합니다.
4. `CONFIG`에서 다음을 확인합니다.
   - `PROJECT_MODE=APPS_SCRIPT_STANDALONE`
   - `STANDALONE_ENABLED=Y`
5. 트리거 2개를 확인합니다.
   - `handleSpreadsheetFormSubmit` — 스프레드시트 Form 제출
   - `runFiveDayReminders` — 매일 지정 시각
6. Lv.5 통과 시 독립 실행기가 같은 흐름에서 인증서 생성과 Discord 공유를 수행합니다.

### 8.3 Make로 복귀

1. `removeStandaloneTriggers()`를 실행합니다.
2. `PROJECT_MODE=MAKE_ASSET_ONLY`, `STANDALONE_ENABLED=N`을 확인합니다.
3. Make SCN-01~03을 Run once로 다시 확인합니다.
4. 이후 Scheduling을 켭니다.

3. 리마인드가 한 번 게시되고 발송 여부가 `Y`가 되는지 확인합니다.

## 10. Discord 전송·재시도 계약

Discord Webhook은 JSON 메시지와 multipart 파일 업로드를 지원하며, 파일 첨부 시 `payload_json`과 `files[0]`을 사용합니다. [[1]](#ref1) [[2]](#ref2)

모든 payload는 다음을 유지합니다.

```json
{
  "allowed_mentions": {
    "parse": []
  }
}
```

Embed는 제목 256자, 설명 4096자, 필드 25개, 한 메시지의 Embed 전체 문자 합계 6000자 제한을 고려해야 합니다. [[3]](#ref3)

Apps Script 구현은 최대 3회 시도합니다.

- HTTP `429`: 응답의 `retry_after`를 읽어 대기
- HTTP `5xx`: 지수형 대기 후 재시도
- 최대 대기: `20000ms`
- 최종 실패: `Discord최근발송상태=실패`; 인증서 공유 실패 시 `인증서발급상태=발급실패`

Discord는 rate limit 응답을 준수해 재시도하도록 안내합니다. [[4]](#ref4) Make에서는 각 Discord HTTP 모듈에 Error Handler를 별도로 구성하여 429의 `retry_after` 또는 `Retry-After`, 5xx의 지수형 대기를 반영하고 최대 재시도 횟수를 제한합니다.

## 11. 인증서 처리 계약

### Make 모드

```text
SCN-02 Lv.5 통과
→ Lv5상태=완료
→ 전체완료여부=완료
→ 인증서발급상태=미발급
→ issuePendingCertificates 시간 트리거
→ PDF 생성 또는 기존 동일 파일 재사용
→ Discord Embed + PDF 직접 첨부
→ 실패/20 MiB 초과 시 Drive 링크 fallback
```

일반적인 Discord 메시지 첨부 한도 조사값은 25 MiB였으나, 이 구현은 안전 여유를 위해 20 MiB를 직접 첨부 기준으로 사용합니다. [[2]](#ref2) Drive fallback이 필요할 때 코드가 링크 공유를 시도하므로 운영자는 해당 파일의 공개 범위가 과도하지 않은지 점검해야 합니다.

### 인증서 상태

- `미발급`: Lv.5 완료 후 발급 대기
- `처리중`: PDF 생성·전송 중
- `발급완료`: Discord PDF 첨부 또는 Drive fallback 성공
- `발급실패`: PDF 생성 또는 Discord 공유 실패

### 멱등키

- 참가 신청: `JOIN|...`
- 레벨 통과: `PASS|{참가자ID}|L{레벨}`
- 리마인드: `REMIND|{참가자ID}|L{현재레벨}|D5`
- 인증서: `CERT|{참가자ID}|V1`

Apps Script 독립 실행기는 `운영로그`의 성공 멱등키를 실제 조회합니다. 반면 현재 Make Blueprint에는 `운영로그` 멱등키의 원자적 선점·조회·완료 기록이 구현되어 있지 않고 상태 열·상호 배타 필터·순차 실행·동시 실행 1에 의존합니다. 따라서 **원 요구의 엄격한 멱등키 기준은 현재 Blueprint만으로 충족하지 못하며, 운영 활성화 차단 FAIL**입니다. Discord 전송 성공 후 상태 갱신 전에 실행이 중단되거나 Watch Rows 이벤트가 재전달되면 중복 게시 가능성이 남습니다.

Make 모드를 활성화하기 전에 각 경로에 다음을 구현해야 합니다.

1. Discord HTTP 전송 전에 `운영로그`에서 `JOIN|...`, `PASS|{참가자ID}|L{레벨}`, `REMIND|{참가자ID}|L{레벨}|D5` 키를 원자적으로 선점합니다.
2. 같은 키가 `처리중` 또는 `성공`이면 전송 경로를 종료합니다.
3. 전송 성공 뒤 `성공`, 최종 실패 뒤 재시도 가능한 실패 상태를 기록합니다.
4. 각 Discord HTTP 모듈에 429 `retry_after`/`Retry-After` 및 5xx 지수형 **최대 3회** Error Handler를 실제로 구성합니다.
5. 위 동작을 Make History로 증명하기 전에는 세 시나리오의 Scheduling을 OFF로 유지합니다.

## 13. 일상 운영

### 매일 점검

- Make History 실패 실행
- `AK(Discord최근발송상태)=실패`
- `AF(인증서발급상태)=처리중` 장기 지속 또는 `발급실패`
- 예정일이 지났지만 `AC=N`인 참가자
- Form 응답 수와 트래커 행 수의 이상 차이
- Discord 메시지의 개인정보 노출

### 변경 관리

- Form 질문 제목을 바꾸면 Apps Script `namedValues`와 Make 열 매핑이 깨질 수 있습니다.
- 시트 열을 이동·삽입·삭제하면 Blueprint 숫자 인덱스가 바뀝니다.
- `setupFridgeChallenge()`를 재실행하기 전에 수정한 `미션설정`과 `메시지템플릿`을 백업합니다.
- Make 수정 전 Blueprint를 백업하되 Webhook URL이 포함되지 않았는지 검사합니다.

## 14. 장애 복구

### Apps Script 권한·설치 실패

1. **Executions**에서 오류 줄과 메시지를 확인합니다.
2. `appsscript.json` 저장 여부를 확인합니다.
3. 조직 관리자에게 필요한 OAuth 범위 허용을 요청합니다.
4. 일시 오류면 `setupFridgeChallenge()`를 재실행합니다. Script Properties가 남아 있으면 기존 자산을 재사용합니다.
5. `selfCheckFridgeChallenge()`를 다시 실행합니다.

### Form 응답 시트 오류

1. 각 Form의 응답 대상이 운영 DB인지 확인합니다.
2. `참가신청_응답`, `미션인증_응답` 탭 이름을 확인합니다.
3. 중복 탭을 정리하되 데이터를 먼저 백업합니다.
4. `setupFridgeChallenge()`를 재실행합니다.

### Make 모듈이 빨간색

1. Google 연결을 재승인합니다.
2. Spreadsheet와 Sheet를 다시 선택합니다.
3. 열 목록을 새로 불러옵니다.
4. 필터와 Row number를 다시 선택합니다.
5. Search Rows의 0건 계속 실행 옵션을 확인합니다.
6. 테스트 DB 복사본에서 `Run once`를 다시 수행합니다.

### Update Row가 다른 열을 지움

1. 즉시 해당 시나리오 Scheduling을 OFF로 합니다.
2. Row number와 Values 매핑을 확인합니다.
3. 비어 있는 동적 토큰이 실제 빈값 쓰기로 처리되는지 확인합니다.
4. 필요한 경우 기존 행을 먼저 읽고 보존할 열도 명시적으로 매핑합니다.

### Discord 429 또는 5xx

1. Make History 또는 Apps Script Executions에서 HTTP 코드를 확인합니다.
2. 429는 `retry_after`에 맞춰 재시도합니다.
3. 5xx는 지수형 대기를 적용합니다.
4. 최종 실패 행은 `AK=실패` 또는 운영로그로 추적합니다.
5. 성공을 확인하기 전 상태를 수동으로 `성공`으로 바꾸지 않습니다.

### Webhook 401·403·404 또는 유출 의심

1. Make Scheduling 또는 독립 실행을 잠시 중지합니다.
2. Webhook이 삭제되었거나 URL이 바뀌었는지 확인합니다.
3. 유출 가능성이 있으면 기존 Webhook을 삭제하고 새로 생성합니다.
4. Apps Script와 Make 저장값을 갱신합니다.
5. 테스트 후 운영을 재개합니다.

### 인증서가 `처리중`에 멈춤

1. Apps Script Executions에서 `issuePendingCertificates` 오류를 확인합니다.
2. 인증서 템플릿과 폴더 접근 권한을 확인합니다.
3. 장시간 중단이 확인되면 데이터 백업 후 상태를 `발급실패`로 변경합니다.
4. `issuePendingCertificates()`를 다시 실행합니다.
5. 동일 인증서 파일명이 재사용되는지 확인합니다.

### 긴급하게 Make에서 독립 실행으로 전환

1. SCN-01~03 Scheduling을 모두 OFF.
2. `installStandaloneTriggers()` 실행.
3. `PROJECT_MODE=APPS_SCRIPT_STANDALONE`, `STANDALONE_ENABLED=Y` 확인.
4. 참가 신청·미션·리마인드·인증서를 테스트.

Make 복귀 시 반드시 `removeStandaloneTriggers()`를 먼저 실행합니다.
